# Business Rules — Expense Manager V2

## บัญชีหลักและบัญชีย่อยสำหรับรายงาน

- บัญชีย่อยผูกกับบัญชีหลักหนึ่งบัญชี ไม่มี ledger หรือยอดเงินจริงซ้ำอีกชุด รายการระบุบัญชีย่อยแยกฝั่งต้นทางและปลายทางได้ และต้องอยู่ภายใต้บัญชีหลักที่เลือก
- ยอดบัญชีย่อยคำนวณด้วยกฎ Ledger เดียวกับบัญชีหลัก โดยจัดผลแต่ละฝั่งตาม sub_account_id กลุ่มว่างรับยอดยกมาและรายการเดิม ผลรวมบัญชีย่อยและกลุ่มว่างต้องตรงบัญชีหลักถึงระดับสตางค์
- RECLASSIFY ใช้จัดกลุ่มยอดภายในบัญชีหลักเดียวกัน ทั้งสินทรัพย์และหนี้สิน ลดกลุ่มต้นทางและเพิ่มกลุ่มปลายทาง ไม่มีรายรับหรือรายจ่ายเพิ่ม ใช้แบ่งยอดยกมาจากกลุ่มว่างและกลับรายการได้
- ชื่อบัญชีย่อยซ้ำได้ข้ามบัญชีหลัก แต่ชื่อที่เปิดใช้ในบัญชีหลักเดียวกันต้องไม่ซ้ำ เปลี่ยนบัญชีหลักของบัญชีย่อยที่สร้างแล้วไม่ได้
- แผนและงวดเก็บบัญชีย่อยร่วมกัน การชำระหนี้ใช้บัญชีย่อยของแผนที่ฝั่งหนี้ ส่วนฝั่งจ่ายเงินเลือกบัญชีย่อยสินทรัพย์ได้ ดอกเบี้ยและค่าธรรมเนียมอยู่ในบัญชีย่อยของแผน การแก้กลุ่มของแผนจะจัดกลุ่มประวัติธุรกรรมที่เชื่อมแผนและใช้บัญชีหลักของแผนนั้นตามไปด้วย โดยคงยอดและวันที่ธุรกรรม
- การกันเงินยังบังคับความเพียงพอที่บัญชีหลัก รายงานแยกยอดกันไว้ตามบัญชีย่อยของงวดเมื่อบัญชีที่กันเงินตรงกับบัญชีหลักของแผน กรณีใช้คนละบัญชีให้แสดงในกลุ่มยังไม่ระบุของบัญชีที่กันเงิน
- รายงานส่วนตัวเลือกดูยอดบัญชีหลักหรือบัญชีย่อยได้ ไฟล์ CSV ข้อมูลรายละเอียดและ Pivot มีชื่อบัญชีหลักและชื่อบัญชีย่อยสำหรับตรวจสอบ
- รายงานสำหรับส่งต่อใช้ API ที่คืนเฉพาะชื่อบัญชีย่อย ยอดปัจจุบัน รายรับ รายจ่าย และประเภทสินทรัพย์/หนี้สิน ส่งออก PNG และ CSV ได้จากตัวอย่างรายงาน กลุ่มว่างไม่รวมในรายงานสำหรับส่งต่อ

ชื่อบัญชีที่ใช้แสดงกำหนดได้ในหน้าบัญชีและข้อมูลหลัก โดยเก็บใน Settings คีย์ `account.display_name.<account_id>` และคงชื่อบัญชี/บัตรใน Accounts.account_name สำหรับแก้ไขข้อมูลหลัก ชื่อแสดงใช้กับตัวเลือกบัญชี กราฟ ตาราง รายงาน และคอลัมน์ชื่อบัญชีที่อ้างอิงใน Transactions, PaymentPlans และ PaymentSchedules เมื่อชื่อแสดงว่างให้ใช้ชื่อบัญชี/บัตร การเปลี่ยนชื่อแสดง refresh projection ย้อนหลังโดยคง ID ยอด และ updated_at ของรายการไว้ CSV ที่ส่งออกใหม่ใช้ชื่อแสดง ส่วนไฟล์ที่เคยส่งออกและ Pivot ที่สร้างไว้ต้องสร้างใหม่เพื่อรับชื่อแสดงล่าสุด

| BR-DM-07 | ต้องมีฟังก์ชันตรวจและซ่อม Projection (`refreshProjections`) ที่คำนวณชื่อใหม่จาก ID ได้ทุกเมื่อแบบ idempotent สำหรับกู้คืนเมื่อ refresh ล้มเหลวกลางทาง |

| BR-DM-10 | ข้อความทุกคอลัมน์ที่ผู้ใช้กรอก (item_name, description, note, ชื่อ Master) ต้องผ่านการป้องกัน Formula Injection (ค่าขึ้นต้นด้วย `=`, `+`, `-`, `@`, Tab, CR ให้เก็บเป็นข้อความ) และ escape ตอนแสดงผลเพื่อป้องกัน XSS |

## 3. Transactions

### 3.1 ทั่วไป

- amount > 0 เสมอ ทิศทางกำหนดโดย Backend จาก transaction_type และประเภทบัญชี
- item_name บังคับ; description, note ไม่บังคับ
- ห้ามลบธุรกรรมจริง ใช้การกลับรายการ (`reversal_of`)
- ป้องกันรายการซ้ำด้วย idempotency_key และแจ้งเตือนรายการที่อาจซ้ำ (วันที่ + ประเภท + ยอด + บัญชีต้นทาง/ปลายทาง + item_name เดียวกัน) — ผู้ใช้ยืนยันบันทึกต่อได้ (`allow_duplicate`)
- client ส่งได้เฉพาะ: transaction_date, transaction_type, from/to_account_id, owner_id, category_id, item_name, description, amount, external_ref, note, source (MANUAL | QUICK_ENTRY); plan_id, reversal_of, *_name, timestamps กำหนดโดย Backend
- **แก้ไข** ได้เมื่อรายการไม่ใช่รายการกลับ, ยังไม่ถูกกลับรายการ, ไม่เชื่อมแผน (plan_id) และไม่ถูกจัดสรรให้งวด; ค่าก่อนแก้เก็บใน OperationJournal.recovery_data (server เท่านั้น)
- **กลับรายการ** แทนการลบ: สร้างรายการใหม่ `reversal_of` = ต้นฉบับ, ประเภท/บัญชี/หมวด/ยอดเดิม, item_name ขึ้นต้น "กลับรายการ: ", note = เหตุผล (บังคับ), วันที่ไม่ก่อนต้นฉบับ; **รายการที่มี reversal_of มีผลทางบัญชีตรงข้ามกับต้นฉบับทุกค่า**; กลับซ้ำ/กลับรายการกลับไม่ได้
- ผลต่อยอดบัญชี (balance ของสินทรัพย์ = เงินคงเหลือ, ของหนี้สิน = หนี้คงค้าง): INCOME to +; EXPENSE from −; TRANSFER from −, to +; CREDIT_PURCHASE from +; CREDIT_PAYMENT from −, to −; CASH_ADVANCE from +, to +; INTEREST/FEE from: สินทรัพย์ −, หนี้สิน +; REFUND to: สินทรัพย์ +, หนี้สิน −; ADJUSTMENT from −, to + (ตาม balance ของบัญชีนั้น)
- รายรับ = INCOME; รายจ่าย = EXPENSE + CREDIT_PURCHASE + INTEREST + FEE − REFUND (TRANSFER, CREDIT_PAYMENT, CASH_ADVANCE, ADJUSTMENT ไม่นับ)
- ระบบยังไม่ห้ามยอดเงินสด/เงินฝากติดลบ (แสดงยอดติดลบให้เห็น)

### 3.2 บัญชีต้นทาง/ปลายทางตามประเภท

ความหมาย: `from_account` = บัญชีที่มูลค่าไหลออกหรือหนี้เพิ่ม, `to_account` = บัญชีที่มูลค่าไหลเข้าหรือหนี้ลด

| transaction_type | from_account_id | to_account_id | category_id |
|---|---|---|---|
| INCOME | ว่าง | บังคับ (สินทรัพย์) | บังคับ (INCOME) |
| EXPENSE | บังคับ (สินทรัพย์) | ว่าง | บังคับ (EXPENSE) |
| TRANSFER | บังคับ (สินทรัพย์) | บังคับ (สินทรัพย์, ต่างจาก from) | ไม่ใช้ |
| CREDIT_PURCHASE | บังคับ (CREDIT_CARD / CASH_CARD / LOAN) | ว่าง | บังคับ (EXPENSE) |
| CREDIT_PAYMENT | บังคับ (สินทรัพย์) | บังคับ (หนี้สิน) | ไม่ใช้ |
| CASH_ADVANCE | บังคับ (CREDIT_CARD / CASH_CARD / LOAN) | บังคับ (สินทรัพย์) | ไม่ใช้ |
| INTEREST / FEE | บังคับ (บัญชีที่ถูกเรียกเก็บ) | ว่าง | บังคับ (EXPENSE) |
| REFUND | ว่าง | บังคับ (บัญชีที่รับคืน) | บังคับ (หมวดของรายการต้นฉบับ) |
| ADJUSTMENT | ระบุอย่างใดอย่างหนึ่ง | ระบุอย่างใดอย่างหนึ่ง | ไม่ใช้; note บังคับ (เหตุผล) |

`from_account_name` / `to_account_name` / `category_name` ว่างเมื่อ ID ที่คู่กันว่าง

ผลทางบัญชีของแต่ละประเภทเป็นไปตาม AGENTS.md §7.3

### 3.5 เวลาที่บันทึกและการเรียง (2026-11-28)

- หน้ารายการแสดงเวลาที่บันทึก (`created_at`, Asia/Bangkok) และแหล่งที่มา (`source`: AI = ผ่าน LINE/API, PLAN = จากแผนชำระ) ใต้รายละเอียดของทุกแถว
- เรียงได้ 2 แบบ: วันที่ทำรายการล่าสุดก่อน (ค่าเริ่มต้น) หรือเวลาที่บันทึกล่าสุดก่อน — รายการจากสลิปใช้วันที่บนสลิปเป็น transaction_date จึงอาจอยู่ย้อนหลัง การเรียงตามเวลาที่บันทึกทำให้เห็นรายการที่เพิ่งบันทึกบนสุด; ตัวกรองเดือนยังกรองตามวันที่ทำรายการ

### 3.4 ตัวช่วยกรอก (2026-11-25)

- คำนวณจากประวัติ Transactions จริงทุกครั้ง **ไม่เก็บข้อมูลเพิ่มและไม่เปลี่ยน schema**
- จัดกลุ่มด้วย ประเภท + ชื่อรายการ (normalize) + บัญชีต้นทาง/ปลายทาง + หมวด + เจ้าของ; ใช้ยอดและวันที่ของรายการล่าสุดในกลุ่ม
- ตัดออก: รายการกลับรายการและที่ถูกกลับแล้ว, ADJUSTMENT, กลุ่มที่อ้างอิง Master ที่ปิดใช้งาน, รายการนอกช่วง lookback (ค่าเริ่มต้น 180 วัน) หรือหลังวันนี้
- **รายการล่าสุด**: เรียงตามวันที่/เวลาบันทึกล่าสุด; **ใช้ประจำ**: กลุ่มที่เกิดใน ≥ 2 เดือน หรือ ≥ 3 ครั้ง เรียงตามจำนวนเดือน → จำนวนครั้ง
- การแตะแม่แบบเพียงเติมฟอร์ม (วันที่คงเป็นวันนี้) ผู้ใช้ต้องตรวจและกดบันทึกเอง; การบันทึกผ่านกฎ §3.1–3.2 และการเตือนรายการซ้ำตามปกติ
- ไม่ใช่การตั้งรายจ่ายประจำอัตโนมัติ: รายจ่ายประจำที่มีกำหนดเวลาใช้ Payment Planner แบบ RECURRING (Phase 4); การปักหมุดแม่แบบเองต้องมีที่เก็บใหม่ (ต้องขออนุมัติ schema)

### 3.3 เงินกู้และการยืมเงินบุคคล (ตัดสินใจ 2026-11-25)

ใช้บัญชีประเภท `LOAN` หนึ่งบัญชีต่อเจ้าหนี้หนึ่งราย (เช่น "ยืมเงิน คุณสมชาย", institution = ชื่อผู้ให้ยืม); ไม่เพิ่มคอลัมน์หรือ enum ใหม่

| เหตุการณ์ | บันทึกเป็น | from → to | ผล |
|---|---|---|---|
| หนี้คงค้าง ณ วันเริ่มใช้ระบบ | `Accounts.opening_balance` ของบัญชี LOAN | — | ยอดหนี้ตั้งต้น |
| รับเงินกู้/ยืมเงินเพิ่ม | `CASH_ADVANCE` (หน้าจอแสดง "รับเงินกู้/เบิกเงินสด") | LOAN → บัญชีสินทรัพย์ที่รับเงิน | หนี้เพิ่ม + เงินเพิ่ม; **ไม่ใช่รายรับ** |
| คืนเงินต้น | `CREDIT_PAYMENT` (หน้าจอแสดง "ชำระหนี้/บัตร") | บัญชีสินทรัพย์ → LOAN | หนี้ลด + เงินลด; **ไม่ใช่รายจ่าย** |
| ดอกเบี้ยที่จ่ายจริง | `INTEREST` แยกรายการ | บัญชีสินทรัพย์ (จ่ายทันที) หรือ LOAN (ทบเข้าหนี้) | รับรู้รายจ่าย |
| ซื้อของโดยตรงด้วยสินเชื่อ (เช่น สินเชื่อผ่อนสินค้า) | `CREDIT_PURCHASE` | LOAN → — | หนี้เพิ่ม + รับรู้รายจ่าย |

- ยอดชำระหนึ่งครั้งที่มีทั้งเงินต้นและดอกเบี้ย ให้แยกเป็น CREDIT_PAYMENT (เงินต้น) + INTEREST (ดอกเบี้ย) เพื่อไม่นับเงินต้นเป็นรายจ่าย
- แผนคืนเงินกู้ใน Payment Planner ใช้ `account_id` = บัญชี LOAN และหมวดหมู่ประเภท EXPENSE ที่ตั้งชื่อชัดเจน เช่น "ชำระหนี้"; หมวดนี้เป็นป้ายสำหรับรายงานแผนเท่านั้น การจ่ายจริงยังเป็น CREDIT_PAYMENT/INTEREST จึงไม่สร้างรายจ่ายซ้ำ — รายงานรายรับรายจ่ายจริงอ่านจาก Transactions ไม่ใช่ยอดแผน
- ยอดหนี้คงเหลือของบัญชี LOAN = opening_balance + CASH_ADVANCE + CREDIT_PURCHASE + INTEREST/FEE ที่ทบเข้าหนี้ − CREDIT_PAYMENT (คำนวณจาก Transactions ไม่ใช่จากแผน)
- **ไม่อยู่ในขอบเขต:** การให้ผู้อื่นยืมเงิน (ลูกหนี้/สินทรัพย์) ต้องเพิ่มประเภทบัญชีใหม่และขออนุมัติ schema ก่อน

## 4. Payment Planner

### 4.1 การสร้างแผน

- ผู้ใช้กรอกครั้งเดียวที่ PaymentPlans: purchase_date, item_name, description, owner_id, category_id, account_id, principal/interest/fee, installment_count, first_saving_month, first_payment_month, due_day (ถ้าทราบ), note
- Backend เติม account_name, owner_name, category_name จาก Master และคำนวณ total_amount
- Backend สร้าง PaymentSchedules หนึ่งแถวต่อหนึ่งงวดด้วย Batch Write โดย **คัดลอกทุกงวด**: purchase_date, plan_type, account_id, account_name, owner_id, owner_name, category_id, category_name, item_name, description, installment_count
- ONE_TIME: installment_count = 1, installment_no = 1
- แสดงตัวอย่างงวดก่อนยืนยันเสมอ

### 4.2 งวดและเดือน

- installment_no และ installment_count แยกคอลัมน์ เป็น Integer; ห้ามเก็บรูปแบบ `1/6` (UI แสดงได้)
- saving_month, payment_month เป็น Integer YYYYMM; งวดที่ n = first_*_month + (n−1) เดือนด้วย calendar arithmetic (202612 → 202701); ปฏิเสธค่าเช่น 202613, 202600, 20261
- due_date = payment_month + due_day; ถ้า due_day เกินวันสุดท้ายของเดือนใช้วันสุดท้าย; ไม่ทราบ due_day ให้ว่าง
- amount_due = total_amount ÷ installment_count ปัดเป็นสตางค์ เศษปรับที่งวดสุดท้าย; แก้รายงวดได้แต่ผลรวมงวดที่ไม่ยกเลิกต้องเท่ากับ total_amount
- ฟอร์มสร้างแผนรองรับดอกเบี้ยคงที่จากเงินต้น × (อัตราต่อปี ÷ 100) × (จำนวนงวด ÷ 12) และค่าธรรมเนียมครั้งเดียวจากเงินต้น × (อัตราค่าธรรมเนียม ÷ 100) ปัดแต่ละยอดเป็นสตางค์ก่อนรวม ผู้ใช้กรอกยอดบาทโดยตรงได้
- เมื่อเลือกเก็บค่าธรรมเนียมในงวดแรก ให้แบ่งเฉพาะเงินต้นและดอกเบี้ย แล้วบวกค่าธรรมเนียมทั้งหมดในงวดแรก หากแก้ยอดเอง งวดแรกต้องครอบคลุมค่าธรรมเนียม ตัวเลือกนี้กำหนดยอดเรียกเก็บรายงวด ส่วนการรับรู้ค่าใช้จ่ายเมื่อชำระหนี้เป็นไปตาม §4.6
- หนึ่งงวด = หนึ่งแถว

### 4.3 การแก้ไขแผน

| ฟิลด์ที่แก้ที่แผน | ผลต่อ PaymentSchedules |
|---|---|
| item_name, description, owner_id, category_id | Propagate ไปทุกงวด (รวมงวดที่ชำระแล้ว เพราะเป็นข้อมูลอธิบาย ไม่มีผลทางการเงิน) และ refresh ชื่อ |
| account_id | อนุญาตเฉพาะเมื่อแผนยังไม่มี Reservations, PaymentAllocations หรือธุรกรรมที่เชื่อมแผน (รวมรายการซื้อด้วยบัตร); มิฉะนั้นต้องยกเลิกแผนและสร้างใหม่ |
| ยอดเงินและเดือนรายงวด, วันครบกำหนด | ใช้ RESCHEDULE ตาม §4.7 คงรหัสงวดและยอดรวม ไม่แก้งวดที่ชำระครบ หน้าจอมีปุ่มเลื่อนทุกงวดที่ค้าง ±1 เดือน (ทั้งสองเดือน เฉพาะเดือนชำระ หรือเฉพาะเดือนเก็บ) แล้วตรวจก่อนยืนยัน |
| installment_count และเดือนเริ่มของแผน | คงข้อมูลเดิม การต่ออายุรายจ่ายประจำเพิ่มงวดต่อท้ายผ่าน RENEW |
| note ของแผน | ไม่กระทบ note ของงวด |

- แก้ owner_id หรือ category_id ของแผน: Transactions ที่เชื่อมกับแผน (plan_id รวมรายการกลับรายการ) เปลี่ยน owner_id และ category_id ตาม (เฉพาะรายการที่มีหมวดอยู่แล้ว CREDIT_PAYMENT คงว่าง) เป็นการจัดประเภทเท่านั้น ไม่เปลี่ยนยอด วันที่ หรือ updated_at และ refresh ชื่อ (ผู้ใช้อนุมัติ 2026-11-26) ส่วน item_name/description ของธุรกรรมไม่ถูกแก้
- บัญชีย่อยของแผน reclassify ธุรกรรมฝั่งบัญชีของแผนตามเดิม
- หน้าแก้รายละเอียดแผนมีช่องเจ้าของ หมวดหมู่ (รายจ่าย) และบัญชี/บัตร ช่องบัญชีถูกปิดเมื่อแผนมีประวัติการเงิน (backend ตรวจซ้ำ)
- ห้ามแก้คอลัมน์ PROJ ของ PaymentSchedules โดยตรง (ทั้งผ่าน API และในชีต)

### 4.4 สถานะและยอด (Derived)

ตาม AGENTS.md §6.3 และ §7.3:

- amount_saved = SUM(RESERVE) − SUM(RELEASE ที่มีผลจริง) โดย RELEASE อัตโนมัติที่ผูกกับการชำระซึ่งถูกกลับรายการแล้วไม่ถูกนับ
- amount_reserved = amount_saved − SUM(CONSUME ของธุรกรรมที่มีผลจริง) — CONSUME ที่ผูกกับธุรกรรมชำระซึ่งถูกกลับรายการแล้วไม่ถูกนับ เงินที่เคยกันไว้จึงกลับมาเป็นกันไว้ในบัญชีเดิมและใช้ชำระใหม่ได้; แถว CONSUME เดิมยังคงอยู่เป็นประวัติ (ตัดสินใจ 2026-11-26)
- amount_paid = ผลรวม allocated_amount ของธุรกรรมที่มีผล (ไม่ถูกกลับรายการ)
- remaining_to_pay = MAX(0, amount_due − amount_paid)
- remaining_to_save = MAX(0, remaining_to_pay − amount_reserved)
- saving_status: CANCELLED ถ้า is_cancelled; NOT_REQUIRED ถ้า remaining_to_pay = 0; SAVED ถ้า remaining_to_save = 0; PARTIAL ถ้า amount_reserved > 0; มิฉะนั้น NOT_SAVED
- payment_status: CANCELLED ถ้า is_cancelled; PAID ถ้า remaining_to_pay = 0; PARTIAL ถ้า amount_paid > 0; มิฉะนั้น UNPAID
- is_overdue = ไม่ยกเลิก AND remaining_to_pay > 0 AND due_date < วันนี้ (Asia/Bangkok)
- remaining_installments = จำนวนงวดในแผนเดียวกันที่ไม่ยกเลิกและ remaining_to_pay > 0 (ค่าเดียวกันทุกงวดของแผน; ห้าม SUM)
- plan_status: CANCELLED เมื่อแผนถูกยกเลิก; COMPLETED เมื่อทุกงวดที่ไม่ยกเลิก PAID; มิฉะนั้น ACTIVE

### 4.5 Reservations และ Allocations

- RESERVE ไม่เกินเงินที่ใช้ได้ของบัญชี; RELEASE/CONSUME ไม่เกินยอดที่กันไว้ในบัญชีนั้นของงวดนั้น; CONSUME ต้องมี transaction_id
- ผลรวม allocation ต่อธุรกรรม ≤ amount ของธุรกรรม; ต่องวด ≤ amount_due; ยอดที่ยังไม่จัดสรรแสดงแยก
- การกันเงินไม่ใช่รายจ่าย; การชำระจริงสร้าง Transactions + PaymentAllocations + CONSUME เฉพาะเงินกันไว้ที่ใช้จริง

### 4.6 แผนผ่อนบัตรเครดิต/สินเชื่อที่เชื่อมรายการซื้อ (2026-11-26)

ไม่เปลี่ยน schema ใช้ `Transactions.plan_id` และ `source = PLAN`

| ตัวเลือกตอนสร้างแผน (`purchase_link`) | ผล |
|---|---|
| `NEW` | สร้าง `CREDIT_PURCHASE` หนึ่งรายการใน operation เดียวกับแผน: from = บัญชีของแผน, amount = principal_amount, วันที่ = purchase_date, หมวด/เจ้าของ/ชื่อรายการ/รายละเอียด/external_ref จากแผน |
| `EXISTING` | เชื่อม `CREDIT_PURCHASE` ที่บันทึกไว้แล้ว (`purchase_transaction_id`) โดยตั้ง plan_id; ต้องเป็นบัญชีเดียวกัน ยอด = principal_amount วันที่ = purchase_date ไม่ถูกกลับรายการ และยังไม่เชื่อมแผนอื่น; ไม่แก้ข้อมูลอื่นของธุรกรรม |
| `NONE` (ค่าเริ่มต้น) | ไม่สร้างหรือเชื่อมรายการซื้อ |

- เชื่อมได้เฉพาะแผน INSTALLMENT / ONE_TIME ที่บัญชีเป็น CREDIT_CARD, CASH_CARD หรือ LOAN, เงินต้น > 0 และ purchase_date ไม่อยู่ในอนาคต; หนึ่งแผนมี CREDIT_PURCHASE ได้หนึ่งรายการ
- **แผนแบบหนี้** = บัญชีของแผนเป็นหนี้สิน และ (มี CREDIT_PURCHASE ที่เชื่อมอยู่ หรือเป็น LOAN ตาม §3.3): การชำระงวดสร้าง `CREDIT_PAYMENT` จากบัญชีสินทรัพย์ → บัญชีของแผน (ลดหนี้ ไม่รับรู้รายจ่ายซ้ำ) แทน EXPENSE; แผนอื่น (รวมแผนบัตรที่ไม่เชื่อมรายการซื้อ) ยังชำระเป็น EXPENSE
- เมื่อชำระแผนแบบหนี้ ให้บันทึกดอกเบี้ยและค่าธรรมเนียมเป็น `INTEREST` และ `FEE` จากบัญชีของแผน โดยผูก external_ref กับ transaction_id ของ CREDIT_PAYMENT ครั้งนั้น
- แผนที่กระจายค่าธรรมเนียมหรือไม่มีการบันทึกตัวเลือก ใช้ยอดสะสมตามกติกาเดิม `floor(ยอดตามแผน × ยอดชำระสะสม ÷ total_amount) − ส่วนที่รับรู้แล้ว`
- แผนที่เลือกค่าธรรมเนียมงวดแรก บันทึกตัวเลือกใน Settings ด้วยคีย์ `plan.fee_timing.<plan_id>` ค่า `FIRST` เมื่อชำระให้คิดเฉพาะส่วนที่จัดสรรให้งวด 1 เป็นสตางค์ตามสูตร `floor(ค่าธรรมเนียมที่เหลือ × ยอดที่จ่ายให้งวด 1 ÷ ยอดค้างงวด 1 ก่อนจ่าย)` จ่ายเฉพาะงวดอื่นรับรู้ค่าธรรมเนียม 0 และเมื่อปิดงวด 1 จะรับรู้เศษที่เหลือครบ
- ในโหมดงวดแรก คิดดอกเบี้ยจากยอดจ่ายหลังหักค่าธรรมเนียมครั้งนี้ ตามสัดส่วนดอกเบี้ยที่เหลือต่อยอดค้างทั้งแผนหลังหักค่าธรรมเนียมที่เหลือก่อนจ่าย การกลับรายการหักยอดดอกเบี้ยและค่าธรรมเนียมของการจ่ายครั้งนั้นออกก่อนคำนวณการจ่ายครั้งถัดไป
- ผลรวมเมื่อชำระครบ: หนี้บัตรกลับเป็น 0 และรายจ่ายรวม = principal + interest + fee เพียงครั้งเดียว
- กลับรายการชำระ (REVERSE_PAY) กลับ CREDIT_PAYMENT พร้อม INTEREST/FEE ที่ผูกกับครั้งนั้น และเงินกันไว้กลับมาตาม §4.5
- ธุรกรรมที่มี plan_id (รายการซื้อ ชำระงวด ดอกเบี้ย) แก้ไขหรือกลับรายการจากหน้ารายการไม่ได้ ต้องจัดการผ่านแผนชำระ
- ยกเลิกแผนไม่กลับรายการซื้อ หนี้ที่เกิดจริงยังอยู่ การปรับงวดและปิดยอดใช้ §4.7–4.8

### 4.7 ปรับตารางงวดที่บันทึกแล้ว (RESCHEDULE)

- แก้เฉพาะงวดที่ไม่ยกเลิกและยังค้างในแผน ACTIVE ส่งรายการงวดที่ค้างให้ครบและไม่ซ้ำ คง schedule_id จำนวนงวด ยอดรวมแผน ประวัติชำระ และหมายเหตุเดิม
- ยอดงวดใหม่ต้องมากกว่า 0 และไม่น้อยกว่ายอดที่จ่ายแล้ว ผลรวมยอดงวดที่แก้ต้องเท่ากับเดิม งวดแรกของแผน FIRST ยังต้องครอบคลุมค่าธรรมเนียม
- เปลี่ยน saving_month / payment_month เป็น YYYYMM และ due_day ได้ อัปเดตวันสิ้นเดือน ปี เลขเดือน และ is_month_different ตามปฏิทิน
- หากเงินกันไว้มากกว่ายอดค้างใหม่ ให้ RELEASE เฉพาะส่วนเกินตามบัญชี ไม่สร้างธุรกรรมรายจ่าย
- บังคับเหตุผลและตัวอย่างก่อนยืนยัน ฝั่ง server ตรวจ version ของแผนและงวดภายใต้ lock อีกครั้ง หากข้อมูลเปลี่ยนต้องตรวจตัวอย่างใหม่

### 4.8 ปิดยอดก่อนกำหนด (SETTLE)

- บังคับเหตุผล บัญชีสินทรัพย์ที่จ่าย วันที่จริง และยอดดอกเบี้ย/ค่าธรรมเนียมที่ยังต้องจ่ายซึ่งเป็น 0 หรือค่าบวก ผู้ใช้ตรวจยอดรวมก่อนยืนยัน
- ยอดปิด = เงินต้นคงค้าง + ดอกเบี้ยที่ยังต้องจ่ายตามยอดปิดจริง + ค่าธรรมเนียมที่ยังต้องจ่ายตามยอดปิดจริง ใช้สตางค์ในการคำนวณ
- เงินต้นคงค้างหักเฉพาะเงินต้นที่ชำระแล้ว แผนหนี้ใช้ INTEREST/FEE ที่รับรู้จริง แผนรายจ่ายใช้สัดส่วนดอกเบี้ย/ค่าธรรมเนียมตามแผน โดย FIRST แยกค่าธรรมเนียมของงวดแรก
- แผนรายจ่ายที่ยกเลิกบางงวดจะตัดภาระคงค้างของงวดที่ยกเลิกออกจากยอดปิด แผนบัตร/สินเชื่อยังคงเงินต้นหนี้จริง การยกเลิกตารางไม่ล้างหนี้
- คงงวดที่ชำระครบ ใช้งวดค้างแรกเป็นงวดรับยอดปิด งวดอื่นคงยอดที่จ่ายจริงและยกเลิกส่วนอนาคตที่ยังไม่จ่าย ปลดเงินกันไว้ที่ไม่ได้ใช้ และปิดสถานะแผนเมื่อบันทึกสำเร็จ
- แผนหนี้สร้าง CREDIT_PAYMENT และ INTEREST/FEE เท่ากับยอดเพิ่มเติมที่ยืนยัน แผนรายจ่ายสร้าง EXPENSE เพียงครั้งเดียว ปรับยอดรวมแผนให้เท่ากับยอดที่เคยชำระ + ยอดปิดจริง
- เก็บ snapshot ยอดและสถานะงวดก่อนปิดใน Settings คีย์ `plan.settlement.<transaction_id>` และ recovery_data ของ OperationJournal โดยไม่เพิ่มคอลัมน์หรือแก้ schema
- ส่งซ้ำด้วย key เดิมไม่สร้างธุรกรรมหรือการจัดสรรซ้ำ กลับรายการปิดยอดจะคืนยอดแผน ตารางงวด และเงินกันไว้เดิม พร้อมรักษาประวัติทั้งหมด
- หลังปิดยอด อนุญาตแก้ข้อมูลอธิบาย/หมายเหตุหรือกลับรายการปิดยอด ต้องกลับรายการปิดยอดก่อนจึงกลับรายการชำระเก่าหรือปรับแผนต่อได้
- RELEASE อัตโนมัติระหว่างชำระผูก transaction_id เพื่อคืนเงินกันไว้เมื่อกลับรายการ รายงานยอดเก็บจริงบันทึกการคืนส่วนนี้ในเดือนที่กลับรายการ ส่วน RELEASE แบบผู้ใช้สั่งโดยตรงคงมีผลตามเดิม

### 4.9 รายการประจำเดือนและบันทึกหลายรายการ (2026-11-26)

- มุมมองรายเดือนอยู่ในหน้าแผนชำระ (แท็บ "รายเดือน") ใช้ข้อมูลชุดเดียวกับหน้าแผน ไม่เรียก server เพิ่ม
- โหมด "ต้องจ่าย" ใช้ `payment_month` และ `remaining_to_pay`; โหมด "ต้องเก็บ" ใช้ `saving_month` และ `remaining_to_save`; แสดงงวดของเดือนที่เลือก รวมงวดที่ทำครบแล้วเพื่อดูผลรายเดือน และแสดง "ค้างจากเดือนก่อน" แยก (เดือนก่อนหน้าที่ยังมียอดคงเหลือ) ไม่แสดงงวด/แผนที่ยกเลิก
- จัดกลุ่มตามบัญชี/บัตร บัญชี/บัตร + บัญชีย่อย บัญชีย่อยของแผน (ชื่อบัญชีย่อยล้วน แผนที่ไม่มีบัญชีย่อยรวมเป็นกลุ่ม "ไม่ระบุบัญชีย่อย") หรือเจ้าของ และกรองเจ้าของได้ สถานะรายเดือนคำนวณจากงวด ไม่มีตารางปิดเดือนแยก
- เลขแสดงผล `#เลขแผน-งวด` (เช่น #12-3) ใช้แยกแผนชื่อเดียวกัน ไม่ใช่รหัสหลักและไม่เก็บในชีต: เลขแผนคำนวณตอนอ่านจากลำดับการสร้าง (created_at แล้วลำดับแถวที่ต่อท้าย) เลขจึงไม่เปลี่ยนเพราะระบบไม่ลบแผน รหัสหลักทุกตารางเป็น running number ต่อตารางตาม AGENTS.md §7.2 (เลขแผนแสดงผลอาจไม่เท่า plan_id) แสดงในหน้าแผน หน้าจัดการ แท็บรายเดือน หน้ายืนยัน และ CSV รายเดือน (คอลัมน์ "เลขที่") ส่วน Pivot ในชีตยังไม่มีเลขนี้
- แท็บรายเดือนแสดงวันที่ทำรายการ (purchase_date) ของแผน
- มุมมองรายปี (ปุ่ม "รายปี" ในกลุ่มปุ่ม รายแผน / รายเดือน / รายปี ของหน้าแผนชำระ): ตาราง 12 เดือนต่อกลุ่มตามการจัดกลุ่มที่เลือก แต่ละช่องแสดงยอดตามแผน (amount_due) และคงเหลือ (remaining_to_pay หรือ remaining_to_save ตามโหมด) ของงวดที่เดือนชำระ/เดือนเก็บอยู่ในปีนั้น ไม่รวมงวดยกเลิก แต่รวมแผนที่จบแล้วเพื่อดูย้อนหลัง มีแถว/คอลัมน์รวม แตะช่องเพื่อเปิดเดือนนั้นในมุมมองรายเดือน และส่งออก CSV สองแถวต่อกลุ่ม (ตามแผน/คงเหลือ) คอลัมน์ YYYYMM
- งวดที่เดือนเก็บต่างจากเดือนจ่าย (`saving_month != payment_month`) ที่ยังไม่ครบ เน้นด้วยแถบส้มและป้าย "เก็บ <เดือน> → จ่าย <เดือน>" พร้อมคำอธิบายจำนวนรายการด้านบน
- `api_monthlyBatch` รับ `{ action: PAY | RESERVE, date, note, items: [{ schedule_id, account_id, amount }] }` สูงสุด 30 รายการ plan_id มาจากงวดในฐานข้อมูล ไม่รับจาก client
- PAY รวมงวดของแผนเดียวกันที่จ่ายจากบัญชีเดียวกันเป็นธุรกรรมเดียว แผนต่างกันเป็นธุรกรรมแยก (หนึ่งรายการต่อแผนเหมือนการชำระทีละแผน) RESERVE เป็นหนึ่งเหตุการณ์ต่องวด กฎทุกข้อใน §4.5–4.6 ใช้ตามเดิมเพราะเรียกขั้นตอนเตรียมข้อมูลเดียวกัน
- ตรวจทั้งชุดก่อนเขียน: รายการใดไม่ผ่าน (ยอดเกิน งวดซ้ำ เงินไม่พอเมื่อรวมรายการก่อนหน้าในชุด บัญชีไม่ใช่สินทรัพย์ แผนปิดยอดแล้ว) ทั้งชุดไม่ถูกบันทึก และข้อความระบุชื่อรายการ
- ใช้ operation_type `PAYMENT_ACTIVITY` เดียวกับการทำรายการทีละแผน งานที่ค้างของแบบหนึ่งจึงบล็อกอีกแบบจน retry สำเร็จ
- หน้ายืนยันแสดงยอดตามคู่บัญชี (บัญชีที่จ่าย → บัตร/สินเชื่อ หรือรายจ่ายจากบัญชี) พร้อมเงินกันไว้ที่จะถูกใช้ ใช้เป็นเช็กลิสต์โอนเงิน บัญชีที่จ่ายเริ่มต้นเป็นบัญชีที่มีเงินกันไว้มากที่สุดของงวดในกลุ่ม
- Dashboard แสดงงานของเดือนปัจจุบัน (รวมงวดค้างจากเดือนก่อน) ตามตัวกรองเจ้าของ/บัญชี และลิงก์ไปมุมมองรายเดือน; ส่งออก CSV ของมุมมองที่แสดงอยู่ได้ (กัน formula injection)

### 4.10 ย้ายเงินกันไว้ระหว่างบัญชี (2026-11-26)

- `api_moveReserve` รับ `{ from_account_id, to_account_id, date, note, transfer, items: [{ schedule_id, amount }] }` สูงสุด 30 งวด บันทึก RELEASE ที่ต้นทางและ RESERVE ที่ปลายทางยอดเท่ากันต่องวด ยอดกันไว้รวมและสถานะของงวดไม่เปลี่ยน
- transfer = true สร้าง TRANSFER ต้นทาง → ปลายทางยอดรวม (เจ้าของ = เจ้าของแผนของงวดแรก) ไม่นับเป็นรายรับรายจ่าย
- ตรวจก่อนเขียน: ต้นทางต่างจากปลายทาง ทั้งคู่เป็นบัญชีสินทรัพย์ (ปลายทางต้องใช้งานอยู่) ยอดไม่เกินที่กันไว้ในต้นทางของแต่ละงวด และปลายทางมีเงินที่ใช้ได้พอ (รวมเงินที่โอนในชุดนี้) ถ้าไม่ผ่านไม่บันทึกอะไรเลย
- RELEASE/RESERVE ของการย้ายไม่ผูก transaction_id เพื่อให้การกลับรายการโอนภายหลังไม่ทำให้เงินกันไว้ถูกนับซ้ำสองบัญชี (ต้องย้ายกลับเองถ้าต้องการ)
- ใช้ operation_type PAYMENT_ACTIVITY ร่วมกับการทำรายการอื่นของแผน จึงกันงานค้างชนกัน

### 4.11 งบใช้จ่ายรายเดือน / รายสัปดาห์ (อนุมัติ 2026-11-26)

- ตั้งที่เมนูหลัก "งบใช้จ่าย": ชื่อ เดือน (YYYYMM) เจ้าของ (ว่าง = ทุกคน) งบทั้งเดือน งบต่อสัปดาห์ (ไม่บังคับ) หมวดรายจ่ายที่นับ (อย่างน้อย 1) และหมายเหตุ
- ยอดใช้ไป = รายจ่ายที่รับรู้ตาม Ledger (EXPENSE, CREDIT_PURCHASE, INTEREST, FEE) ของหมวดในงบ ในเดือนของงบ และของเจ้าของถ้าระบุ รายการกลับรายการหักออก ไม่นับรายรับ/โอน/ชำระหนี้บัตร
- สัปดาห์ = วันที่ 1–7, 8–14, 15–21, 22–28, 29–สิ้นเดือน สัปดาห์ก่อนสุดท้ายได้ weekly_amount (ไม่เกินงบที่เหลือ) สัปดาห์สุดท้ายได้ส่วนที่เหลือ ถ้าไม่ระบุ weekly_amount แบ่งตามจำนวนวัน
- ยกยอด: ยกมา = งบสะสมก่อนสัปดาห์ − ใช้ไปสะสม; สัปดาห์นี้เหลือ = งบสะสมถึงสัปดาห์นี้ − ใช้ไปสะสมถึงสิ้นสัปดาห์นี้ (ติดลบได้เมื่อใช้เกิน)
- ใช้ได้วันละ = ยอดเหลือ ÷ จำนวนวันที่เหลือรวมวันนี้ ปัดลงเป็นสตางค์ และเป็น 0 เมื่อเหลือติดลบ (แสดงทั้งแบบสัปดาห์นี้และทั้งเดือน)
- แก้ชื่อ/เจ้าของ/ยอด/หมายเหตุ = แก้แถวเดิม; เปลี่ยนเดือนหรือชุดหมวด = ปิดงบเดิม (is_active FALSE) แล้วสร้างงบใหม่ ไม่ลบแถว; ปิดงบได้ คัดลอกงบจากเดือนก่อนได้ (ข้ามชื่อที่มีแล้วและหมวดที่ปิดใช้งาน)
- แสดงผล: หน้างบใช้จ่าย (ตารางสัปดาห์), การ์ด "งบใช้จ่ายเดือนนี้" ในหน้าภาพรวม (เดือนปัจจุบันเสมอ) และข้อความใต้ช่องหมวดตอนบันทึกรายการ
- ชีต Budgets/BudgetCategories สร้างเองเมื่อบันทึกงบครั้งแรก ถ้ายังไม่มีชีต หน้าอื่นทำงานตามปกติและเห็นเป็นไม่มีงบ

### 4.12 งบทริป / โครงการ (EVENT budget, อนุมัติ 2026-11-27)

รายละเอียดและเหตุผล: [event-budget-plan.md](event-budget-plan.md)

- Budgets.budget_kind = `EVENT`: ชื่อ, ยอดงบ > 0, start_date–end_date (end ≥ start, ไม่เกิน 366 วัน), เจ้าของ (ว่าง = ทุกคน), หมายเหตุ; budget_month = เดือนของ start_date, weekly_amount = 0, ไม่มีแถว BudgetCategories; แถวเดิมที่ budget_kind ว่าง = MONTHLY
- ชื่องบทริปที่เปิดใช้ต้องไม่ซ้ำกัน (ไม่สนตัวพิมพ์/ช่องว่างหัวท้าย)
- แก้ชื่อ ยอด ช่วงวันที่ เจ้าของ หมายเหตุ = แก้แถวเดิม; เปลี่ยนชื่อ → refresh `Transactions.budget_name` (projection ไม่เปลี่ยน updated_at) + audit `RENAME_BUDGET` หนึ่งครั้ง; `refreshProjections()` ครอบคลุม budget_name
- เปลี่ยนเจ้าของงบเป็นคนหนึ่งไม่ได้ถ้ามีรายการของเจ้าของอื่นใช้งบนั้นอยู่
- ปิดงบ (is_active FALSE): เลือกกับรายการใหม่ไม่ได้ รายการเดิมคงอ้างอิงและนับยอดเหมือนเดิม; เปิดใช้อีกครั้งได้
- `Transactions.budget_id` ("ใช้จากงบทริป"): เฉพาะ EXPENSE, CREDIT_PURCHASE, INTEREST, FEE, REFUND; งบต้องเป็น EVENT ที่เปิดใช้ (หรือเป็นค่าเดิมของรายการที่แก้); งบที่ระบุเจ้าของ → รายการต้องเป็นของเจ้าของคนนั้น; ไม่จำกัดวันที่/บัญชี/หมวด; แก้รายการโดยไม่ส่ง budget_id = คงค่าเดิม
- กลับรายการคัดลอก budget_id จากต้นฉบับ ยอดใช้ไปจึงลดลงเอง; ธุรกรรมจากแผนชำระยังไม่มีช่องงบ (ระยะ E1)
- ใช้ไป = Σ `Ledger.effectsOf(t).expenseSatang` ของรายการที่ budget_id ตรงกัน (REFUND และรายการกลับรายการเป็นค่าลบ); คงเหลือ = งบ − ใช้ไป (ติดลบได้); ระหว่างทริป ใช้ได้วันละ = คงเหลือ ÷ วันที่เหลือ (ปัดลงเป็นสตางค์ ไม่ติดลบ); แยกยอดตามหมวดและบัญชี
- **รายการที่ระบุงบทริปไม่นับในงบรายเดือน** (ผู้ใช้เลือก 2026-11-27); Dashboard รายงาน และ Pivot นับตามปกติ (งบไม่ใช่ผลทางบัญชี)
- งบรายเดือนเดิม: แสดง/คัดลอก/แก้เฉพาะ MONTHLY; บันทึกงบรายเดือนเขียน budget_kind = MONTHLY
- หน้าจอ: เมนูงบใช้จ่ายมีส่วน "งบทริป/โครงการ" (ไม่ขึ้นกับเดือนที่เลือก) พร้อมปุ่ม "ดูรายการ" ที่กรองหน้ารายการด้วยงบ (ไม่กรองเดือน); ฟอร์มรายการมีช่อง "ใช้จากงบทริป" เฉพาะประเภทที่ใช้ได้และงบของเจ้าของนั้น/ทุกคน; หน้าภาพรวมแสดงงบทริปที่ยังไม่จบในการ์ดงบ; CSV/Pivot รายการมีคอลัมน์ budget_name

### 4.13 กันเงินให้งบทริป (E3, อนุมัติ 2026-11-28)

- ชีต `BudgetReservations` (แยกจาก Reservations ของแผนชำระ): RESERVE / RELEASE ต่อบัญชีสินทรัพย์ (CASH/BANK/E_WALLET) ของงบ EVENT ที่เปิดใช้
- กันไว้สุทธิต่อบัญชี = Σ RESERVE − Σ RELEASE; **เงินกันที่มีผล = MIN(กันไว้สุทธิรวม, MAX(0, งบ − ใช้ไป))** แบ่งตามสัดส่วนบัญชี (ปัดลงเป็นสตางค์ บัญชีสุดท้ายตามลำดับ ID รับเศษ) — ลดลงเองเมื่อใช้จ่ายในงบ (รวมรูดบัตร) และกลับมาเมื่อกลับรายการ/คืนเงิน (ผู้ใช้เลือก 2026-11-28)
- **ปิดงบทริป = เงินกันที่มีผลเป็น 0 ทันที** ไม่เขียน RELEASE; เปิดใช้อีกครั้งกลับมามีผล (ผู้ใช้เลือก 2026-11-28)
- RESERVE ไม่เกินยอดที่ยังต้องกัน (งบ − ใช้ไป − กันไว้สุทธิ) และไม่เกินเงินที่ใช้ได้ของบัญชี (หลังหักเงินกันของแผนชำระและงบทริปทั้งหมด); RELEASE ไม่เกินกันไว้สุทธิของบัญชีนั้น
- "เงินที่ใช้ได้จริง" = ยอดบัญชี − เงินกันของแผนชำระ − เงินกันที่มีผลของงบทริป ทุกจุด: Dashboard (ยอดรวมและรายบัญชี/บัญชีย่อย — งบทริปอยู่ในกลุ่มยังไม่ระบุบัญชีย่อย), แถบยอดหน้ารายการ, `balances` ของ API/LINE, ตรวจยอดตอนกัน/ชำระ/ย้ายเงินกันของแผนชำระ (`Budgets.accountHolds`)
- การกันเงินไม่ใช่ธุรกรรม ไม่กระทบยอดบัญชี รายรับรายจ่าย งบรายเดือน หรือ Pivot
